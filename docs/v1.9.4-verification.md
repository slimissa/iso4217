## What changed

ADR 0014 (`docs/decisions/release-harness.md`), ten decisions. The release
script is tested the same way the registry is: it runs from `main()` against a
fake remote, one mutation per v1.9.3 defect, and every mutation is killed.

### D1 — What the harness tests

The whole pipeline, run from `main()` of `scripts/release.sh` copied into a
fixture repository, plus one test per path. Function extraction stays for what
it already covers (the existing `test_release_*.py` files); the harness adds what
function extraction cannot see: an ordering bug between stages, or a stage
swallowing another's failure.

Three classes of test, and the red-first rule applies to the class, not the count:

1. **Red-first** — fails on the v1.9.3 script, passes on the fixed one.
2. **Characterization** — passes today and must pass after.
3. **Mutation-killed** — passes today, passes after, fails on the mutant.

### D2 — The fake remote

A bare git repo in a temp dir as `origin`; real `git` throughout; a stub `gh` on
`PATH`, driven by a state file; a push made to fail with a `pre-receive` hook.
The stub `gh` reports a run only for a commit origin holds (GitHub does not
report one for a commit it never received — that was M25's blind spot). Every
test builds its own fixture; nothing is shared.

### D3 — `--force` and an existing tag

The tag state is read from origin first (`git ls-remote --tags origin`), then
from the local repo. A published tag is never moved (RELEASE_PATTERN.md
invariant 8). `--force` recreates a tag that exists only locally (a release
whose tag push failed).

### D4 — The verification doc

The stub retires; the second commit stays. `write_verification_doc` writes a
complete document and checks it with `tools/check_verification_doc.py` before
committing it. The tag commit's hash cannot be written inside the commit it
names, and the CI result cannot exist before the commit is pushed, so the
follow-up commit is structural, not a workaround. If the generated doc would
fail the checker, the script exits 8 and does not commit it.

### D5 — Dry-run

`--dry-run` runs the preconditions, then bump, regenerate, and gate in a
throwaway copy of the tree (`cp -a` to `mktemp -d`, removed on exit), and never
touches the operator's tree. A dry-run that cannot tell you whether the gate
passes is a plan, not a dry-run.

### D6 — Exit codes

0 success, 1 precondition problem, 2 usage, 3 could-not-run, 4 generator/bump/gate
failed (tree mutated), 5 commit/push failed, 6 CI not green, 7 tag failed,
8 verification doc failed (released and tagged; only the doc is missing). The
0–3 meanings are unchanged from RELEASE_PATTERN.md; 4–8 extend by stage.

### D7 — Preconditions

Ten, not seven: `check_head_at_origin`, `check_on_main`, `check_clean_tree`,
`check_tag_free`, `check_changelog_section`, `check_manifest_has_version`,
`check_workflows_covered`, `check_gh_ready`, `check_version_consistency`,
`check_no_orphan_variables`. Each has a test that forces it from `main()`.

### D8 — Bump functions

The seven functions (eight sites — `iso_json` writes `meta.version` and
`meta.updated`) move out of `release.sh` into `scripts/bump_version.py`, one
callable per site. Each is idempotent, fails loudly, reads its result back, and
never reads the clock (`release.sh` computes `TODAY` once, UTC, and passes it
in). The prior inline Python heredocs and `sed -i` bumps silently did nothing on
a pattern miss.

### D9 — The gate accumulates

The gate runs every step and reports every failure; the header comment that said
"stops at the first failure" is corrected.

### D10 — A failed gate does not roll back

No automatic rollback. The preconditions guarantee the tree was clean at the
start, so the printed recovery (`git checkout -- .`) is exact; an automatic
rollback would destroy the evidence of what failed.

## Known limits

- **A re-run on a later day rewrites `meta.updated`.** ADR 0014 names this; a
  re-run bumps the *date* without re-bumping the version. v1.9.5 candidate.
- **`check_workflows_covered` exempts workflows by name prefix** (`monitor`,
  `fetch`, `refresh`, `update`, `schedule`). A push-triggered `update-*.yml`
  would be silently unpolled. v1.9.5 candidate.
- **`check_verification_doc.py --all` still reports 24 findings on pre-v1.9.2
  docs** (v1.5.0, v1.5.4, v1.7.4, v1.7.5). The default mode (the gate's mode)
  is clean. The `--all` semantics are P5-11, v1.9.5.
- **The `docs/audits/fifth-pass.md` → `third-pass.md` rename** is v1.9.5.
- **D4's CI assertion.** The release commit's CI and the fix commit's CI are
  both recorded in §8.1 above. The harness proves the doc *would* pass the
  checker; green CI on the *real* commits is observed, not proven.
- **The doc itself is the third commit.** The release script wrote a doc,
  refused to commit it (exit 8, per D4). The v1.9.4 checker fix (fcc04cf) makes
  a fenced code span not a real marker. This doc was then written by hand and
  committed by the maintainer (see git log).
