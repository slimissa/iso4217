# Data Layers

The ISO 4217 Currency Registry follows a three-layer data model. This
document names the layers, states the rule that governs them, and maps
every artifact in the repository to its layer.

The model is not enforced by code. It is a discipline — a way of deciding
where a new file belongs and what a new tool is allowed to read. The
discipline is what makes the registry reproducible: any artifact can be
traced back to the commit that produced it, and any derived artifact can
be regenerated from the one below.

---

## The three layers

| Layer | Contents | Rule |
|-------|----------|------|
| **RAW** | `iso4217.json` | Never modified by tooling. The single source of truth. Every field change is a human commit. |
| **CURATED** | SQL, CSV, TSV, Parquet exports; wrapper copies; the CLI | Regenerated from RAW by deterministic tools. Never hand-edited. `--check` mode verifies they match. |
| **AGGREGATED** | *(not yet implemented — planned for v1.7.0)* | Answers questions, not facts. One row per `(region, currency)`, or per `(anchor, count)`. Reads CURATED, never RAW. |

The RAW layer is one file. The CURATED layer is eight flat-file exports
plus two embedded wrapper copies plus a CLI. The AGGREGATED layer is
empty — the registry has not yet needed it.

---

## The rule

> A layer may only assume what the layer below guarantees.

Consequences, spelled out:

- `tools/export_sql.py` reads `iso4217.json` and produces SQL. It does not
  read CSV or Parquet.
- `tools/export_csv.py` reads `iso4217.json` and produces CSV/TSV. It does
  not read the SQL export.
- `tools/export_parquet.py` reads `iso4217.json` and produces Parquet. It
  does not read the CSV export.
- `tools/sync_wrappers.py` copies `iso4217.json` into the Go and Rust
  wrapper directories. It does not read any CURATED artifact.
- The CLI reads `iso4217.json` via the Python wrapper. It does not read
  the SQL export.
- A future `tools/export_aggregated.py` will read a CURATED artifact (SQL
  or Parquet), not `iso4217.json`.
- No tool writes to `iso4217.json`. It is edited by hand, in a commit, with
  a CHANGELOG entry.

The rule cuts in one direction: a tool may read the layer below it, never
the layer above it, and never a sibling within the same layer to build a
new artifact.

---

## Why this matters

The RAW layer can be replayed from git — checkout any tag, and you have
the exact `iso4217.json` that produced that release.

The CURATED layer can be regenerated from RAW — run the four generators
in the right order, and you have every export. The `--check` mode of each
generator proves the committed file matches what the tool would produce.

The AGGREGATED layer will be regenerable from CURATED — when it exists,
running its generator against any historical tag of the SQL or Parquet
export will produce the aggregate as of that release.

The result is a chain of reproducibility:

    git commit  →  iso4217.json  →  sql/csv/parquet  →  aggregates

Every artifact in the repository can be traced back to the commit that
produced it, and every artifact except `iso4217.json` itself can be
regenerated from the one above it.

This is the same discipline the course describes for a batch pipeline —
*"le code de la couche aggregated ne parse jamais de JSON"* — applied to
the registry's own file structure.

### AGGREGATED

*(empty — planned for v1.7.0)*

Planned artifacts:

| File | One row per | Reads |
|------|-------------|-------|
| `currencies_by_region.parquet` | (region, currency) | `iso4217.parquet` joined with a future `iso3166.parquet` |
| `pegs_summary.parquet` | anchor currency | `iso4217.parquet` |
| `coverage_timeline.parquet` | ISO amendment | CHANGELOG + git history |

None of these exist yet. When they do, their generator will read CURATED,
not RAW.

## How to add a new artifact

When the registry needs a new derived file, the decision is:

1. **Is it a fact about ISO 4217?** It belongs in RAW — add it to
   `iso4217.json` and regenerate the CURATED exports.
2. **Is it a projection of `iso4217.json`?** It belongs in CURATED — add a
   generator, add a CI gate, add a `--check` mode.
3. **Is it an aggregation of two or more CURATED artifacts?** It belongs in
   AGGREGATED — wait until v1.7.0, or place it in `tools/export_aggregated.py`
   when that file exists.

The rule about which layer a tool may read is what makes each artifact
auditable. If a generator reads from two layers, the artifact it produces
no longer has a single upstream dependency, and the chain of
reproducibility breaks.
