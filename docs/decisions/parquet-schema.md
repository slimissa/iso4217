# ADR 0002 — Parquet export schema

**Status:** Accepted
**Date:** 2026-09-16
**Context:** v1.5.2 — Parquet export and formal layering

## Context

The registry ships five consumption formats as of v1.5.1: JSON (the source),
four SQL dialects, four CSV/TSV dialects, and the CLI. These cover relational
databases, spreadsheets, shell scripts, and programmatic lookups from four
languages.

They do not cover one important case: **analytical query engines**. Pandas,
Polars, DuckDB, Spark, Snowflake, BigQuery, and every warehouse loader in
production use today read Parquet natively. Loading a 300-row CSV into any of
them works, but forces type inference, loses the distinction between "empty
string" and "no value", and cannot push column selection down to the reader.

The v1.5.0 review noted that the course's format matrix — CSV, JSON, Parquet,
Avro — has four rows and the registry filled three. Parquet was the missing
cell. This ADR records the schema decisions for closing that gap.

## Decision

Add a single Parquet file, `iso4217.parquet`, regenerated by
`tools/export_parquet.py` from `iso4217.json`. The file uses the same eleven
columns as the CSV export but with native Parquet types and explicit null
semantics.

### Column set and types

| Column | Type | Nullable | Source |
|--------|------|----------|--------|
| `code` | `string` | no | `entry["code"]` |
| `numeric_code` | `string` | no | `entry["numeric"]` |
| `name` | `string` | no | `entry["name"]` |
| `minor_units` | `int8` | no | `entry["minor_units"]` |
| `symbol` | `string` | yes | `entry.get("symbol") or ""` |
| `entity` | `string` | yes | `entry.get("entity") or ""` |
| `status` | `string` | no | derived: `"active"` or `"withdrawn"` |
| `is_independent` | `bool` | no | `entry["is_independent"]` |
| `pegged_to` | `string` | yes | `entry.get("pegged_to")` |
| `peg_type` | `string` | yes | `entry.get("peg_type")` |
| `peg_rate` | `float64` | yes | `entry.get("peg_rate")` |

The column *names* are identical to the CSV export's. A consumer switching
between the two sees the same schema. The only differences are the *types*.

### Null semantics

`pegged_to`, `peg_type`, and `peg_rate` are `null` when not applicable. They
are **not** empty strings. This is the substantive difference from the CSV
export, and it is the reason to choose Parquet over CSV for anything involving
analysis.

A query like `WHERE pegged_to IS NOT NULL` returns exactly the pegged
currencies. The equivalent CSV query would need `WHERE pegged_to != ''`, and
the consumer would have to know that empty string means "not applicable" — an
implicit convention with no way to enforce it.

The four cases in the current data:

| Case | `pegged_to` | `peg_type` | `peg_rate` |
|------|-------------|------------|------------|
| Independent currency (121 rows) | `null` | `null` | `null` |
| Single-currency peg (44 rows) | code | `"single"` | float |
| Basket peg (1 row) | description | `"basket"` | `null` |
| Undisclosed peg (1 row) | description | `"undisclosed"` | `null` |
| Withdrawn currency (135 rows) | `null` | `null` | `null` |

`symbol` and `entity` are declared nullable but currently always contain
either a value or an empty string. The nullability is forward-looking: if
future data represents "no symbol" as `null` rather than `""`, the schema
already accommodates it without a migration.

### Metadata

The Parquet footer carries exactly three key-value entries:

| Key | Value | Source |
|-----|-------|--------|
| `iso4217.version` | e.g. `"1.5.2"` | `iso4217.json` → `meta.version` |
| `iso4217.updated` | e.g. `"2026-09-16"` | `iso4217.json` → `meta.updated` |
| `iso4217.amendment` | e.g. `"179"` | `iso4217.json` → `source.last_amendment_applied` |

No `created_by`, no `timestamp`, no `git_commit`. Parquet's metadata block is
a place for values that describe the file to a reader, not a place to record
provenance. Provenance lives in `docs/PROVENANCE.md` and in the git tag.

The three keys are read back by `--check` mode and asserted by tests. They
make the file self-describing: a consumer who receives only the `.parquet`
file can tell which registry version produced it.

### Row order

Active currencies first, sorted by `code` ascending. Withdrawn currencies
second, sorted by `code` ascending. Identical to the SQL and CSV exports.
This is not a semantic requirement of Parquet — Parquet has no inherent row
order — but it is the invariant that makes a row-for-row cross-check between
the three exports a straightforward comparison.

### Compression and row groups

Snappy compression (pyarrow's default). One row group. No tuning. At 302 rows
× 11 columns, the file is around 15 KB — smaller than the CSV exports, and
smaller than the JSON source. Multiple row groups are a scale optimization
this file will never need; if the registry grows past 100,000 rows, revisit.

## Consequences

### What consumers gain

- **Native types.** `minor_units` is an `int8`, not the string `"2"`. A
  query like `WHERE minor_units = 3` works without casting.
- **Native nulls.** `WHERE pegged_to IS NOT NULL` correctly filters. A
  consumer no longer has to know that empty string means "not applicable".
- **Columnar reads.** `SELECT code, name FROM ...` reads only those two
  columns from disk. On a 300-row file this is invisible; on a joined
  warehouse table with millions of rows, it is 10× — 100× faster.
- **Self-describing.** The three metadata keys tell a reader which registry
  version produced the file, without opening the JSON.

### What changes in the repository

- One new artifact at the root: `iso4217.parquet`.
- One new generator: `tools/export_parquet.py`.
- One new test file: `tests/test_export_parquet.py`.
- One new CI gate: `check-parquet-export`.

Nothing existing changes. The SQL, CSV, TSV, and CLI exports are untouched.

### What `--check` does differently

`export_sql.py --check` and `export_csv.py --check` compare bytes. This works
because SQL and CSV are text formats with deterministic writers.

`export_parquet.py --check` **cannot** compare bytes. Parquet's format permits
different row-group sizes, dictionary-encoding decisions, compression block
boundaries, and metadata key ordering, all producing byte-different files
with identical logical content. A byte comparison would report "stale" on
every run that pyarrow chose a different-but-valid layout.

Instead, `--check` compares logical content:

1. Parse the committed file with `pyarrow.parquet.read_table`.
2. Regenerate the table in memory.
3. Compare column names, column count, and column types.
4. Compare every value with `.to_pydict()`.
5. Compare the metadata key-value maps.

This is slower than a byte comparison (it parses the file) but correct. The
trade-off is documented in the generator's module docstring so that a reader
who notices the absence of `cmp` does not assume it is a bug.

## Alternatives considered

**Option A — No Parquet export; tell consumers to use CSV.**
Rejected. Pandas and Polars can read CSV, but the type and null loss forces
every consumer to write the same coercion logic. The Parquet file exports
that logic once, in a typed schema.

**Option B — Parquet with CSV-compatible types (all strings, no nulls).**
Rejected. This would make the Parquet export a byte-for-byte equivalent of
the CSV export with a different container. The entire point of adding
Parquet is to use its type system and its null semantics.

**Option C — Multiple Parquet files, one per category (active, withdrawn,
non-ISO).** Rejected. The SQL and CSV exports are single-table for a reason:
a consumer filters by `status` rather than choosing between files. Parquet
follows the same pattern.

**Option D — Avro instead of Parquet.**
Rejected. Avro is a row-oriented wire format, optimized for streaming and
for schema evolution in Kafka. Parquet is a column-oriented storage format,
optimized for analytical reads. The registry is a reference table, read in
full and joined, not a stream. Parquet is the correct choice for the
analytics use case; Avro would be correct if the registry published to a
topic.

**Option E — Iceberg or Delta Lake table format.**
Rejected for v1.5.2. Those formats solve problems (concurrent writers,
time travel, sub-second queries over huge partitions) the registry does not
have. They are logged as v1.7.0+ candidates.
