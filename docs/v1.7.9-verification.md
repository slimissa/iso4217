## What changed

One addition and one consequence.

### Added — `tools/check_readme_drift.py`

Four checks against `README.md`, run as a subprocess against the
repository:

1. **links** — every relative link resolves to a tracked file or a
   directory.
2. **tree** — every name in the Project Structure block exists in
   the tree (by basename or path component; template placeholders
   are skipped).
3. **counts** — every count claim matches its source of truth.
   Four patterns today: `167 active currencies`, `135 withdrawn
   currencies`, `21 non-ISO instruments`, and `N-check gate`
   (where N is a word or digit, compared against the number of
   `run_gate_step` calls in `scripts/release.sh`).
4. **adrs** — ADR numbers are unique across `docs/decisions/*.md`,
   and every `ADR NNNN` cited in the README is declared by a file.

The tool is wired into CI's fast workflow and into `release.sh` as
the fourteenth gate step, between `check_country_codes.py` and
`check_cross_language.sh`. Both run the same tool; a claim that
passes locally cannot fail in CI.

Eight tests in `tests/test_check_readme_drift.py` cover each check
plus the fatal path, each against a minimal fake repo in
`tmp_path`.

### Changed — `README.md`

The release-pipeline section now says `sixteen-check gate` and
names `README drift` in the enumerated list of checks. The count
was `fifteen` before this release; the check found the drift the
moment it was wired into the gate, before the README was updated
to match.

### First catch — the check caught its own arrival

Adding the check to the gate grew the gate from fifteen steps to
sixteen. The README still said `fifteen-check gate`. The check
named it:

    DRIFT: [counts] gate step count: readme says 'fifteen' (15) actual=16

That is the whole argument for the check in one line: a claim the
tree no longer supports fails before the release can ship.

### Second catch — the release-claims manifest

`tools/release_claims.json` asserts, for v1.7.9, that
`README.md` contains `sixteen-check gate` and that
`scripts/release.sh` contains `check_readme_drift.py`. Both were
intended but neither had landed when the first `release.sh 1.7.9`
was run. The gate failed at `check_release_claims.py` with two
`[FAIL]` lines and did not create a tag. After the two edits were
applied (via `/tmp/finish_v179.py`, not by hand), the gate passed
and the release proceeded.

This is operator-hygiene rule 6b in `RELEASE_PATTERN.md` — *"The
commit is not the working tree"* — observed twice in one release,
in the same two-file pattern. The rule already exists; the
release is its fourth recorded instance.

## Known limits of the drift check

The check is honest about what it does not do. These limits are
not defects; they are the boundary at which the check stops being
useful and the reader has to look for themselves.

- **Tree check verifies basenames and path components**, not full
  nested paths. A file moved between two directories with the same
  basename passes. A strict path-reconstruction pass is a possible
  v1.7.10 or later; it is not urgent because README tree rewrites
  are rare.
- **Link fragments (`#section`) are not validated.** Only the file
  path is checked. GitHub's anchor generation rules are fiddly
  enough that a wrong fragment check would be worse than no
  fragment check.
- **Count checks cover four patterns.** A new claim in the README
  is not checked until its pattern is added. The check is a guard
  against known-drift classes, not a proof of the README's
  statements.
- **The tool reads from disk, not from git.** A file that exists
  in the working tree but not in `HEAD` passes the link check.
  The gate runs against a clean tree (precondition 1), so this is
  not reachable in practice.
